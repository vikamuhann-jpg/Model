# FlowGuard: Full End-to-End Research and Implementation Plan

## 1. Project Title

> **FlowGuard: A Graph-Based, Temporal and Resource-Efficient Anti-Money Laundering Detection System**

### Core idea

FlowGuard will analyze financial transactions as a **dynamic transaction graph**, extract graph-based and temporal behavioural features, and use machine-learning models to identify potentially suspicious transactions.

The project will begin by reproducing an established **Graph Feature Preprocessor (GFP) + XGBoost** approach. After creating a reliable baseline, you will design and evaluate new features or algorithms to improve:

* Suspicious-transaction detection
* Detection of complex laundering patterns
* False-positive reduction
* Feature-extraction speed
* Memory efficiency
* Explainability
* Real-time processing capability

The research will follow three stages:

```text
REPRODUCE
    ↓
ANALYSE LIMITATIONS
    ↓
DESIGN AND EVALUATE IMPROVEMENTS
```

---

# 2. Problem Statement

Traditional AML systems often rely on:

* Fixed transaction-amount thresholds
* Rule-based alerts
* Individual transaction analysis
* Manually defined suspicious patterns

However, money laundering may involve a sequence of transactions distributed across several accounts.

For example:

```text
Account A
   │ ₹10,00,000
   ▼
Account B
   │ ₹9,80,000
   ▼
Account C
   │ ₹9,50,000
   ▼
Account D
```

Individually, each transaction may appear ordinary. However, the complete transaction path may indicate layering or fund movement.

Therefore, FlowGuard will investigate:

> **How can graph-based, temporal and value-flow information improve AML detection while maintaining acceptable processing time, memory usage and false-positive rates?**

# 3. Research Objectives

## Primary objective

Develop a reproducible graph-based AML detection pipeline using synthetic financial transactions and evaluate whether additional temporal, value-flow and adaptive graph features improve upon an existing GFP-based baseline.

## Secondary objectives

1. Build a clean and reproducible AML data pipeline.
2. Convert financial transactions into a directed temporal graph.
3. Reproduce the relevant GFP feature-extraction approach.
4. Train a transaction-only XGBoost baseline.
5. Train a graph-feature-based XGBoost baseline.
6. Analyse false positives and false negatives.
7. Design new features based on observed limitations.
8. Measure accuracy and computational efficiency.
9. Perform ablation studies.
10. Build an explainable AML risk-scoring interface.
11. Demonstrate the complete system using an API and dashboard.

# 4. Important Research Clarification

Your uploaded IBM material provides two different but related resources:

### IBM synthetic AML data material

The IBM presentation describes synthetic financial transactions, interconnected entities and laundering patterns such as fan-in, fan-out, cycles, scatter-gather and gather-scatter. It also references IBM’s AML data repository and AMLSim.  

### Graph Feature Preprocessor paper

The GFP paper describes graph-pattern-based features and vertex-statistical features that can be combined with gradient-boosting models. It reports improvements in minority-class F1 scores when graph features are added to XGBoost or LightGBM. 

However:

> **Do not assume that the AMLSim dataset and the exact datasets used in the GFP paper are identical.**

Before implementation, you must verify:

* Dataset compatibility
* Available transaction columns
* Label format
* Timestamp format
* Graph structure
* GFP implementation availability
* Exact GFP version and configuration

Until this is verified, describe your first implementation as:

> **A GFP-based or GFP-inspired graph-feature AML baseline**

Do not claim exact reproduction prematurely.

# 13. Phase 7 — Leakage-Safe Temporal Splitting

This is one of the most important parts of the project.

For a transaction at time `T`, the model must only use information available at or before `T`.

```text
Prediction time = T
       ↓
Use only information known ≤ T
```

## Initial split

Use a chronological split such as:

```text
Earliest 70% → Training
Next 15%     → Validation
Latest 15%   → Testing
```

The percentages can be adjusted after inspecting the dataset, but they must be fixed before comparing models.

## Important rules

* Do not randomly shuffle transactions across time.
* Do not use future transactions to calculate historical features.
* Do not calculate global graph statistics using the complete dataset.
* Do not use future labels to construct features.
* Fit scalers or encoders only on the training data.
* Apply class-balancing methods only to the training partition.

## Additional evaluation splits

### A. Standard temporal split

Measures future-like performance.

### B. Unseen-pattern split

Train on some laundering patterns and test on different or composite patterns.

### C. Hard-negative split

Include legitimate but structurally complex activities, such as:

* Payroll
* Treasury transfers
* Merchant settlement
* Supply-chain payments
* Regular business fund movements

This evaluates whether the model can distinguish suspicious graph structures from legitimate complex behaviour.

# 15. Phase 9 — Build the Transaction Graph

Represent the financial system as a directed graph.

```text
Account = Node
Transaction = Directed Edge
```

Example:

```text
A ──₹10,00,000──▶ B
B ──₹9,80,000───▶ C
C ──₹9,50,000───▶ D
```

## Edge attributes

Each edge should store:

```text
transaction_id
timestamp
amount
currency
payment_type
label
```

## Graph representation

For the initial prototype, you can use:

* Python dictionaries
* Adjacency lists
* NetworkX for small-scale analysis
* Pandas or Polars for tabular operations
* PyArrow or Parquet for intermediate storage

For larger datasets, consider:

* CSR-style graph structures
* Incremental adjacency maps
* Specialized graph-processing libraries
* Disk-backed storage
* Streaming processing

## Important design decision

Do not construct the entire future graph when calculating features for an earlier transaction.

The graph must evolve according to transaction time:

```text
Transaction 1 arrives
       ↓
Graph updated
       ↓
Features calculated
       ↓
Transaction scored
       ↓
Transaction 2 arrives
```

# 23. Phase 17 — Research Innovation Stage

Do not implement all novel ideas simultaneously.

## Research direction A — Temporal Flow Motifs

Existing graph features may detect structural patterns but may not fully capture the timing of fund movement.

Develop features such as:

* Time between consecutive hops
* Time from source to final destination
* Transaction burst duration
* Average time between intermediaries
* Time-decayed path activity
* Temporal ordering of graph motifs
* Multi-scale time-window statistics

Example:

```text
A → B at 10:00
B → C at 10:02
C → D at 10:04
```

Potential feature:

```text
rapid_three_hop_transfer = 1
```

---

## Research direction B — Value-Flow Features

Structural features may identify a path without understanding how much value is preserved or lost.

Develop:

* Amount-retention ratio
* Inflow-to-outflow ratio
* Value dissipation
* Amount splitting score
* Amount aggregation score
* Flow conservation deviation
* Percentage of funds transferred onward
* Source-to-final amount ratio

Example:

```text
A sends ₹10,00,000 to B
B sends ₹9,80,000 to C
C sends ₹9,50,000 to D
```

Potential features:

```text
retention_ratio = 950000 / 1000000
value_loss_ratio = 1 - retention_ratio
```

---

## Research direction C — Behavioural Novelty

Instead of only checking whether a pattern exists, measure whether it is unusual for a specific account.

Potential features:

* New-counterparty score
* New payment-type score
* Deviation from historical behaviour
* Sudden degree increase
* Sudden amount-distribution change
* Account activity novelty
* Rare-pattern score

Example:

> An account normally sends money to two known suppliers but suddenly sends funds to 25 new accounts.

---

## Research direction D — Risk-Adaptive Graph Expansion

Instead of exploring the same neighbourhood size for every transaction, use a risk-based expansion strategy.

```text
Incoming transaction
        ↓
Initial one-hop analysis
        ↓
Low-risk?
   ┌────┴────┐
   │         │
  Yes        No
   │         │
Stop     Expand to 2-hop
             ↓
        High risk?
             ↓
        Expand further
```

Potential benefit:

* Less computation for ordinary transactions
* More graph context for suspicious transactions
* Reduced average feature-extraction cost

This must be evaluated carefully because adaptive exploration can introduce selection bias or miss suspicious patterns.

---

## Research direction E — Multi-Resolution Temporal Features

Use multiple time windows:

```text
5 minutes
1 hour
6 hours
1 day
7 days
```

Extract features at each resolution:

* Transaction count
* Amount sum
* Counterparty count
* Fan-in
* Fan-out
* Cycle participation
* Flow velocity

This may help detect both:

* Rapid laundering
* Slow layering

---

## Research direction F — Heterogeneous Graph Features

Represent different entity types separately:

```text
Person
Company
Bank account
Merchant
Supplier
```

Instead of treating every node as an identical account, introduce:

* Node type
* Relationship type
* Ownership relationship
* Employment relationship
* Supplier relationship
* Account relationship

This direction should only be attempted if the selected dataset contains the required entity information.

## Rules

* Keep the dataset fixed.
* Keep the split fixed.
* Keep the model family fixed where possible.
* Keep the evaluation threshold-selection process fixed.
* Add one feature group at a time.
* Report both benefits and drawbacks.

A new feature is useful only if it provides measurable value.
